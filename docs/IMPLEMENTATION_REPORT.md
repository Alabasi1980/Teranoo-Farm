# تقرير تنفيذ الدفعة الأولى + دفعة الإصلاح 1B — مزرعتي: رحلة الازدهار

## 1. ما نُفذ في الدفعة الأولى ودفعة الإصلاح 1B
- **هيكل التطبيق وفصل المسؤوليات**:
  - فصل تعريفات المحتوى والأسعار والأزمنة في `src/content/crops.ts`.
  - فصل منطق اللعبة والاقتصاد والتوقيت ومنحة الإنقاذ وحساب المستوى والهدف التمهيدي في `src/game/rules.ts` و`src/game/types.ts`.
  - فصل خدمات Firebase ومنسّق المزامنة وتصنيف أخطاء الاتصال في `src/firebase/config.ts` و`src/firebase/connectionCheck.ts` و`src/firebase/farmRepository.ts` و`src/firebase/syncLogic.ts` و`src/firebase/syncCoordinator.ts` و`src/firebase/errors.ts`.
  - بناء مشهد ثلاثي الأبعاد Low-Poly بـ Three.js + React Three Fiber + Drei في `src/scene/*` يشمل 6 قطع أرض، وبئرًا ومستودعًا مركّبين من أجزاء متعددة، وسياجًا وأشجارًا، وخامات إجرائية، وإضاءة شمسية دافئة، ومؤثرات جزيئية، ومعالجة تعذر WebGL.
  - بناء واجهة عربية **RTL** متجاوبة للحاسوب والهاتف في `src/components/*`، مع مؤثرات صوتية إجرائية عبر Web Audio API (`src/audio/soundEffects.ts`).
- **إصلاحات سلامة الحفظ والاتساق في 1B**:
  - تمرير الحالة المراد حفظها صراحةً (`retry_pending`، منحة الإنقاذ، وإعادة البداية، والتعديلات المتتالية) دون الاعتماد على قراءة `ref` قبل إعادة رسم React، مع فرض تطابق `state.ownerUid === uid` قبل كل كتابة.
  - ترقيم كل لقطة محلية معلقة برقم تسلسلي (`seq`) وعدم حذف اللقطة إلا إذا طابق `seq` المؤكد من الخادم، مع إعادة ضبط `baseRevision` للتعديلات الأحدث ومتابعة حفظها بالتسلسل، وعدم إظهار «تم الحفظ» أو ادعاء نجاح الحفظ المحلي عند فشله.
  - عزل الجلسات عبر `sessionId` واشتراك `onAuthStateChanged` لمرة واحدة، وحفظ التعديلات المعلقة تحت `uid` الأصلي عند تسجيل الخروج، وتسلسل «مزرعة جديدة» خلف أي حفظ جارٍ مع تعطيل اللعب والضغط المكرر أثناء التحميل/التعارض/إعادة الضبط.
  - تحويل الإنشاء الأولي للمزرعة إلى معاملة `runTransaction` ذرية (`runInitialFarmCreationInTx`) لا تكتب إلا إذا كان المستند غير موجود.
  - توحيد الكتابة بطابع الخادم `serverTimestamp()` والتحقق من `request.time` في قواعد `firestore.rules` الكاملة المشددة.
  - تصنيف نتائج `testFirestoreConnection()` بدقة بين استجابة الخادم المتوقعة (`permission-denied` على مسار الفحص)، وانقطاع الشبكة، ونقص/خطأ قاعدة البيانات، ونفاد الحصة، وأخطاء الخدمة.

### ب. البناء وفحص الأنواع وفحص قواعد الأمان
- `npm run lint` (`tsc --noEmit`): ناجح بدون أخطاء.
- `npm run build` (`vite build`): ناجح بدون أخطاء.
- `npx eslint firestore.rules`: ناجح بدون أخطاء أو تحذيرات (فحص ساكن لبنية القواعد؛ ولا يُعد اختبارًا لسلوك القواعد وقت التشغيل).

### ج. الفحص الحي في المتصفح (Chromium عبر Playwright)
- فحص شاشة البداية (`http://localhost:3000`) ووضع المعاينة المحلي (`?autostart=1`) على سطح المكتب والهاتف مع 0 أخطاء console/page.

## 4. القيود التقنية وما يتطلب اختبارًا يدويًا
- **محاكي Firestore المحلي (Firestore Emulator)**: لا يتوفر Java JRE داخل حاوية البيئة الحالية؛ لذلك لم تُنفّذ اختبارات القواعد سلوكيًا مقابل المحاكي محليًا.
- **تسجيل الدخول بحساب Google الفعلي والكتابة الحية إلى Cloud Firestore**: تتطلب نافذة OAuth تفاعلية من المستخدم؛ لذا تظل دورة الإنشاء الأولي والكتابة والتعديل والتعارض الحية بحساب Google بحاجة إلى تحقق يدوي في المتصفح الفعلي.
